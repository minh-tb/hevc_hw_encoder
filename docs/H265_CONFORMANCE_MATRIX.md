# ITU-T H.265 (V11 01/2026) Normative Conformance Matrix

> **Target Standard**: ITU-T Recommendation H.265 (V11, 01/2026) — *High efficiency video coding* (`T-REC-H.265-202601-I_PDF-E.pdf`, 734 pages).  
> **Reference Software**: Fraunhofer Heinrich Hertz Institute HM-18.0 (`HM/source/Lib/`).  
> **Hardware RTL Base**: `rtl/` (Verilog-2001 / SystemVerilog-2012 targeting AMD UltraScale+ and Intel Cyclone V).  
> **Calibration Anchor**: `0-based PDF Page Index = Printed Spec Page + 17` (calibrated via `scripts/extract_h265_clauses.py` from running footers/headers).  
> **Integer Exactness Mandate**: All decoding/in-loop filtering equations in ITU-T H.265 are 100% fixed-point integer arithmetic (Clause 5.2 & 5.8). Zero floating-point discrepancies permitted.

## Encoder Subset & Unimplemented Features vs. ITU-T H.265 & HM 18.0

Every bitstream produced by this hardware encoder is **100% standard-compliant Main10 syntax** (verified `Max Diff = 0` against HM 18.0 reference decoding). However, to meet single-FPGA LUT/BRAM/DSP budgets and `188.50 MHz` timing closure (`27,785 cycles/CTU`), the RTL intentionally **subsets** or **omits** several optional ITU-T H.265 specification tools and simplifies HM 18.0's floating-point multi-pass RDO search.

Entries are classified as:
- **`SUBSET`**: Valid normative encoder restriction (decoder compliance intact; restricts coding flexibility/configurations).
- **`NOT IMPLEMENTED`**: Optional ITU-T H.265 syntax tool, profile, or signaling mechanism omitted from both RDO and bitstream writer.
- **`SIMPLIFIED RDO`**: Non-normative encoder decision/search heuristic compared to HM 18.0 (`HM/source/Lib/TLibEncoder/`), directly trading coding efficiency for hardware throughput.

### How These Gaps Explain the Measured `+145.52%` BD-Rate vs. `~200×` Speedup

On `Foreman 128×128` 10-bit across $QP \in \{22, 27, 32, 37\}$, this RTL trades coding efficiency (`+145.52%` BD-Rate / `-5.02 dB` BD-PSNR) for real-time deterministic throughput (**`1,696.1 fps` @ `188.50 MHz` Fmax**, `~200×` faster than single-threaded HM 18.0 `TAppEncoder.exe` `~8.4 fps`). Ranked by estimated contribution to the bitrate overhead:
1. **Top-down heuristic CU split (`G-13`) + `4`-mode Luma rough screening (`G-12`)**: Single largest Intra/split penalty, since diagonal edges (`modes 2..9, 11..25, 27..34`) are bypassed and CU splitting cannot verify exact CABAC bit cost.
2. **Symmetric mirrored L1 MV (`G-16`) + `4×4` L0-only ME (`G-18`) + simplified Merge (`G-17`) + `MAX_REF = 1` / Low-Delay GOP (`G-05`)**: Forces bidirectional overhead without independent L1 refinement, combined merge, or multi-reference choice.
3. **`PART_2Nx2N`-only CUs (`G-07`) + `RQT depth = 0` (`G-08`)**: Prevents sub-CU rectangular splits (`2N×N`, `N×2N`, `AMP`) and sub-CU transform splitting (`TU < CU`).
4. **No `RDOQ` (`G-19`) / `SDH` (`G-22`) / `TS` (`G-21`)**: Leaves zeroed-worthy high-frequency coefficients and sign bypass savings unexploited.
5. **Slice-constant QP (`G-11`) & BO-only non-last-CTU / non-merging SAO RDO (`G-24`, `G-25`)**: Modest secondary overhead across CTU headers and flat regions.
